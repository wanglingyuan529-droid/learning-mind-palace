# 2026-10-31 学习日记

> 今天量很大：Set 三兄弟 + 哈希 + 一整套树。

## 🎯 今天一句话

**Set 家族三兄弟就三点差别：HashSet 不保序、靠 hashCode+equals 去重；LinkedHashSet 多一个保序；TreeSet 会排序，并且把「比较结果为 0」当成重复。**

## ✅ 学到了什么

### Java · 哈希值（hashCode）

- 是什么：给对象算出来的一个「编号」，拿来快速定位。
- String 的算法：`h = 31 * h + 字符编码`（不断累乘 31 再加下一个字符）。
- 为什么需要它：有了编号就不用挨个比，直接奔着编号去，这就是**快速查找**的来源。
- ⚠️ 注意：hashCode **不是内存地址**，见文末订正第 1 条。

### Java · HashSet

- 是什么：**去重**的集合，**不保证顺序**（放进去什么顺序，取出来不一定）。
- 底层：HashSet 内部就是包了一个 HashMap，所以是 **数组 + 链表 + 红黑树**。
- **去重是两道关卡，缺一不可**：

| 顺序 | 比较什么 | 作用 |
| --- | --- | --- |
| 第 1 关 | `hashCode()` | 算出该去哪个「桶」 |
| 第 2 关 | `equals()` | 桶里逐个确认是不是真的一样 |

- 只做第 1 关（重写 equals 不重写 hashCode）：内容相同的两个对象会算出不同哈希、落到不同桶，**两个都被加进去**，去重失效。
- 契约定律：**equals 相等 → hashCode 必须相等**；反过来（hashCode 相等）不要求 equals 也相等，那只是「撞桶」。

### Java · LinkedHashSet

- 只比 HashSet 多一个能力：**保证插入顺序**。其余完全一样。
- 底层在哈希表之外多挂了一条双向链表串起顺序。

### Java · 树形结构

- 术语：根节点、父节点、子节点、叶子节点、左/右子节点。
- **树的高度**：从根往下走到最远叶子的层数。
- **BST（二叉查找树）**：左子树全小、右子树全大 → 每比一次砍掉一半，和二分查找同一个思路。
- **退化**：按顺序插入（1,2,3,4…）会退化成一条链表，查找退回到 O(n)。
- **AVL（平衡二叉树）**：任意节点的左右子树**高度差 ≤ 1**，查得稳但维持代价高。
- **红黑树**：用颜色约束形状，**最长路径 ≤ 2 × 最短路径**，比 AVL 宽松，插入删除的代价更小 —— 所以 Java 的 TreeMap / TreeSet / HashMap 扩容后的桶都用它。

**红黑树五条规则**（今天背下来的）：

1. 每个节点非红即黑
2. 根节点必须是黑
3. 叶子节点（NIL 空节点）都是黑
4. 红节点的子节点必须是黑（不能红红相连）
5. 从任一节点到其所有叶子的路径上，经过的黑节点数量相同

### Java · TreeSet

- 是什么：**自动排序 + 自动去重**的 Set。
- 排序两条路：

| 方式 | 规则写在哪 | 什么时候用 |
| --- | --- | --- |
| `Comparable` | 写在自己类的 `compareTo` 里 | 这个类只有一套排序规则 |
| `Comparator` | 创建 TreeSet 时传进去 | 同一个类要好几种排序（分数升序/降序/按名字） |

- **去重判据**：`compareTo` / `compare` **返回 0 就算重复，直接丢弃**（不看 equals）。
- **坑**：没实现 Comparable 的类放进 TreeSet，**加第一个元素不报错，加第二个才抛 `ClassCastException`** —— 因为第一个没有可比较的对象。
- 取舍：Comparable 一个类只能有一套；要多种规则就上 Comparator。

## 🔍 自测（先遮住答案）

> [!question]- Q1：两个对象 equals 相等、hashCode 不等，放进 HashSet 会怎样？
> 两个都留下来了，去重失败。
> 因为 HashSet 先按 hashCode 找桶，hashCode 不等 → 落到不同的桶 → 两关只过了半关，根本没机会用 equals 去比。
> 这就是为什么重写 equals 必须同时重写 hashCode。

> [!question]- Q2：一个没实现 Comparable 的类，往 TreeSet 里加第一个元素会抛异常吗？
> 不会。第一个元素进树时没有别的节点跟它比，所以不触发比较。
> 加**第二个**才抛 `ClassCastException` —— 这时它必须和第一个比大小。
> 这个坑难查，因为报错位置和你以为的位置对不上。

> [!question]- Q3：为什么 `compareTo` 返回 0 的元素会被 TreeSet 丢掉？
> 因为 TreeSet 判断"重复"的标准就是比较结果为 0，它压根不看 equals。
> 所以如果你把 compareTo 写成"只比姓名"，那么同名不同人就只剩一个了 —— 排序字段选错，数据会被静默吃掉。

## ⚠️ 今天最容易记错的 3 处

> [!warning] 1. hashCode 不是内存地址
> 常见误解是"hashCode 比的是内存地址"，**不对**，而且前半句和后半句会自相矛盾：
> - `Object` 的默认 `hashCode()` 与**对象身份**相关（HotSpot 里通常由内存地址派生或按随机种子生成），但它不是地址本身；
> - `String`、`Integer` 这些类**重写了 hashCode**，是按**内容**算的（String 就是 `31 * h + 字符编码`）。
> 一个算内容、一个说地址，两套说法并存，说明这块还没打通。记住一句话：**hashCode 是个由对象信息算出来的编号，怎么算由类自己决定。**

> [!warning] 2. equals 默认比引用，重写后比内容
> 说反了容易乱：
> - `Object.equals()` 的默认实现 = **比是不是同一个对象**（等价 `==`）；
> - `String` 等类**重写后**比的是**内容**。
> 所以"equals 比哪个"取决于类有没有重写，不能一概而论。

> [!warning] 3. 「两个条件」的正确关系
> 不是"随便少一个会误添加"，而是**顺序上就轮不到第二个条件**：
> - 只重写 equals → hashCode 不同 → 进不同桶 → 去重失效
> - 只重写 hashCode → 撞同一个桶后靠默认 equals 比身份 → 还是不同 → 去重失效
>
> 正确说法：**equals 相等则 hashCode 必须相等**，两者要成套重写。
