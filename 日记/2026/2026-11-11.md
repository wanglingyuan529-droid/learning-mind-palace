# 2026-11-11 学习日记

> 两条线一起开：Java 异常（程序出问题时的那套机制），Docker（程序跑不起来时的那套解法）。

## 🎯 今天一句话

**异常是"出事了怎么办"的流程设计，Docker 是"在我这儿能跑、在你那儿跑不了"的解法——一个管运行时的意外，一个管环境的不一致。**

## ✅ 学到了什么

### Java · 异常体系

**异常 = 程序运行中出了问题，Java 用一个对象来表示这件事。**

顶层是 `Throwable`，往下分三支：

```
Throwable
├── Error              通常不处理（JVM 层面出事了，你也救不了）
└── Exception
    ├── RuntimeException   运行时异常 → 可以不处理
    └── 其他 Exception     编译时异常 → 必须处理，否则编译不过
```

**怎么判断一个异常是哪一类**：看继承关系。

- 是 `Error` 的子孙 → Error
- 是 `RuntimeException` 的子孙 → 运行时异常，可以不处理
- 是 `Exception` 的子孙、但**不是** `RuntimeException` 的子孙 → 编译时异常，必须处理

（原稿写成"exception 不继承 run 就是编译时异常"，方向是对的，补完整就是上面这句。）

**异常的两个作用**：
1. **提示错误** —— 告诉你哪儿出了什么事
2. **控制流程跳转** —— 不用一层层 return，直接跳到 catch

### Java · 不写 try-catch 会怎样（JVM 默认处理）

```
异常往上抛 → 一直抛到方法调用链顶端 → 抛到 JVM
                                            ↓
                          打印异常信息到控制台，然后终止程序
```

这就是为什么没捕获的异常会"红字刷屏然后程序挂了"。它不是在报错，是 JVM 按默认流程走完了。

### Java · throw 和 throws

| | throw | throws |
| --- | --- | --- |
| 在哪 | **方法体里** | **方法签名上** |
| 干什么 | 真的抛出一个异常对象 | 声明"我这个方法可能会抛这些异常" |
| 作用 | 制造并抛出 | 提醒调用者：你处理，或者继续往上甩 |

**你那个比喻挺准**：`try` 是监控，`catch` 是保安，`throw` 是故意制造混乱的小偷。

但小偷只负责制造混乱（抛出），**不负责收拾**——收拾是 catch 的活。

`throws` 是另一种东西：它不抛异常，只是在**门口贴个告示**"此处可能有危险，进来的人自己当心"。

**多个 catch 的顺序**：子类在前，父类在后。

```java
catch (FileNotFoundException e) { ... }   // 子类先
catch (IOException e) { ... }             // 父类后
```

写反了会编译报错——父类能吃掉一切，排在后面的子类永远轮不到，Java 直接不让你写。

### Java · 自定义异常

**作用**（你写的两点都对）：

1. **让错误信息业务化**：不用 `Exception("something failed")` 这种废话，改成 `余额不足异常`，一眼知道是什么业务问题
2. **异常链，保留根因**：把底层异常包进来，别把现场毁掉

```java
throw new BalanceNotEnoughException("余额不足", cause);  // cause 就是根因
```

### Docker · 它到底解决什么问题

**一句话**：把「代码 + 依赖 + 环境配置」打包成一个整体，做到**在哪儿跑都一样**。

"我这能跑、客户机不能跑"就是它的原动力——版本、插件、软件、路径这些差异，全被装进同一个盒子。

**C/S 架构**：`docker` 命令是**客户端**，向本机的 **docker 守护进程**发请求，由守护进程干活。所以你敲的每条 docker 命令，本质都是发了个请求给本机的服务。

### Docker · 三个核心概念

| 概念 | 是什么 | 类比 |
| --- | --- | --- |
| **镜像 image** | 打包好的只读模板 | 安装包 / 光盘 |
| **容器 container** | 基于镜像跑起来的实例 | 光盘正在播放 |
| **仓库 registry** | 存放镜像的地方，默认 Docker Hub | 应用商店 |

**关系**：一个镜像可以启动**多个容器**，一个容器只对应一个镜像。

**run 的完整逻辑**（你最后总结的那句，很准）：

```
先看本地有没有这个镜像 → 有就直接用 → 没有就去仓库拉 → 拉到了再启动容器
```

### Docker · 为什么比虚拟机小那么多

原稿写"docker 是只有内核"，**这句要改**（见订正）。

准确的说法：**容器和宿主机共享同一个内核**，镜像里装的是"应用 + 依赖库 + 精简的用户空间"，**不含完整的操作系统**。

虚拟机不一样——每个 VM 里都是一整套**完整的操作系统**（内核 + 系统服务 + 后台进程），几十个 VM 就是几十套系统在同时运行。

所以差距不是"少个内核"，是**少了几十遍的整套系统**。

### Docker · 安装后必做的一步

把当前用户加进 `docker` 组：

```bash
sudo usermod -aG docker $USER   # 然后注销重登，或重启 docker 服务
```

不加的话每条 docker 命令都得 `sudo`，烦且容易搞乱文件权限。但这里有个安全常识，见补充 2。

**验证安装**：

```bash
docker run hello-world
```

看到那行欢迎语，说明客户端、守护进程、镜像拉取、容器启动这条链路全通了。

## 🔍 自测（先遮住答案）

> [!question]- Q1：为什么多个 catch 必须"子类在前，父类在后"？
> 因为 catch 是**从上往下匹配**的，谁先匹配上谁执行，后面的直接跳过。
> 父类（比如 `Exception`）能匹配所有子类异常。如果它排在前面，**所有异常都被它截走**，后面的子类分支永远走不到——编译器直接报错"不可达"。
> 所以顺序必须是：越具体的越靠前，越宽泛的越靠后。

> [!question]- Q2：`throw` 和 `throws`，一个抛异常一个不抛，那 `throws` 到底干什么？
> `throws` **自己不会抛任何异常**，它只是一份声明，写在方法签名上：
> "我这个方法执行时可能往外扔这几种异常，调用我的人要有心理准备。"
> 它的作用是**把处理责任推给调用者**——你不处理，就得在你的方法签名上也写 throws，一层层往上。
> 一句话：`throw` 是真动手，`throws` 是写告示。

> [!question]- Q3：为什么说 Docker 比虚拟机"小那么多"？省掉的具体是什么？
> 省掉的是**整套操作系统**。
> - 虚拟机：每个 VM 里跑一个完整 OS（内核 + 系统服务 + 后台进程），几十个 VM 就是几十套系统
> - 容器：**共享宿主机的内核**，镜像里只有"应用 + 依赖库 + 精简的用户空间"
>
> 所以不是"少个内核"，是少了几十遍重复的系统。启动快也是同因——不用冷启动一整个 OS。

## 📎 补充：两个值得记住的

> [!note] 1. 镜像的分层：这才是"快"的真正原因
> 镜像是**一层层叠出来的**，每条构建指令产生一层，层与层之间可以共用。
> 两个好处：
> - **拉取快**：本地已有某些层，只下载缺的那几层
> - **省磁盘**：两个镜像共用一个基础层，只存一份
>
> 在 Docker Hub 拉镜像时看到 "pull complete" 一条条刷，就是在下载各个层。

> [!note] 2. 加入 docker 组，等于给了 root 权限
> `docker` 组的成员能启动容器，而容器可以挂载宿主机任意目录、以 root 身份运行。
> 所以**加入 docker 组不只是个便利设置，实质上是提权**。
>
> 这不代表不该加（日常开发加是常规做法），但要知道这个口子的分量：**别把来路不明的镜像随手跑起来**。

## ⚠️ 一处要订正

> [!warning] 「docker 是只有内核」——这个说法不对
> 容器里**没有自己的内核**，它**共享宿主机的内核**。但镜像里装的东西远不止"内核"：
>
> | | 虚拟机 | 容器 |
> | --- | --- | --- |
> | 内核 | 每个 VM **自带一套** | **共享宿主的**，自己不带 |
> | 操作系统 | 完整（内核 + 系统服务 + 后台进程） | 没有，只有精简的用户空间 |
> | 镜像里有什么 | 一整个系统 | 应用 + 依赖库 + 基础文件 |
> | 启动 | 冷启动整个系统，慢 | 直接起进程，快 |
>
> **打个比方**：虚拟机是"每户一套独立的水电煤"，容器是"整栋大楼共享水电煤，每户只装自家的家具"。
>
> 所以"小、快"的来源是：**不用为每个实例重复准备一整套运行环境**——不是"只有内核"这么简单。
