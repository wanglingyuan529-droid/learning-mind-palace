## ✅ 学到了什么

### Java · HashMap 源码参数（今天背下来的）

| 参数 | 值 | 什么意思 |
| --- | --- | --- |
| 默认容量 | **16** | 初始化时底层数组的长度 |
| 负载因子 | **0.75** | 装到 75% 就准备扩容 |
| 扩容倍数 | **2 倍** | 每次扩容，容量翻一倍 |
| 链表转红黑树 | 链表 ≥ 8 **且** 数组 ≥ 64 | 两个条件同时满足才转 |
| 红黑树退回链表 | 节点数 ≤ 6 | 删到够少就退回去 |

算一笔账就懂了：容量 16、负载 0.75 → 装到 **12 个**就该扩容了（不是 16 个装满才扩）。

**为什么要扩容**：Entry 越装越多，哈希冲突概率上升，链表变长，查询从 O(1) 退化。扩容就是重新分散，把桶变多。

### Java · 这几个数字背后的「为什么」

> 知道数字不够，能说出原因才算懂。

**① 为什么容量一定要是 2 的幂？**

因为算下标时用的是 `(n - 1) & hash`（位运算），不是 `hash % n`（取模）。

当 n 是 2 的幂时，`n - 1` 的二进制全是 1，位与运算刚好等价于取模，而且**位运算比取模快得多**。所以容量被强制要求是 2 的幂——扩容翻倍，也是为了让容量始终是 2 的幂。

**② 为什么负载因子是 0.75？**

一个纯权衡：

| 调大（比如 1.0） | 调小（比如 0.5） |
| --- | --- |
| 省内存，但冲突多、查询慢 | 冲突少、查得快，但浪费空间 |

0.75 是官方实测的折中点，命中概率和空间开销都比较平衡。

**③ 为什么转红黑树还要求数组 ≥ 64？**

因为数组还小的时候，**扩容比重构更划算**。数组只有 16 或 32 时，桶里挤了 8 个，与其费劲把链表变成树，不如直接扩容把元素重新打散，冲突自然就缓解了。所以 64 这个条件是"先扩容试试，实在不行再转树"的意思。

### Java · 可变参数

```java
public static int sum(int... nums) { ... }
```

- `int...` 表示 **0 个或多个** int，调用时 `sum()`、`sum(1)`、`sum(1,2,3)` 都合法。
- **本质就是 `int[]`**：编译器在调用处自动把参数打包成数组，方法体里你就把它当数组用。
- 规则：一个方法只能有一个可变参数，且**必须放在参数列表最后**。

### Java · 练习：随机抽取器

**① 概率控制：按比例抽男/女生**

思路是把区间按比例切开，落在哪段就抽谁。**关键是分母要想清楚**：

```java
int r = random.nextInt(100);     // 0 ~ 99，一共 100 个数
if (r < 70) {
    // 70% —— 落在 0~69，正好 70 个数，占 100 的 70%
} else {
    // 30% —— 落在 70~99
}
```

等价写法是缩小分母：`random.nextInt(10) < 7` 也是 70%。

> ⚠️ 这里容易混：**「取 0~69」本身不构成 70%**，得说清楚分母是 100。
> 如果直接写 `nextInt(70)`，那生成的全在 0~69 里，等于 100%，就不是概率控制了。

**② `Collections.shuffle(list)`：直接打乱**

- 作用：把 List 里的元素**随机重排**，原地修改，不返回新列表。
- 用途：抽签、洗牌、随机点名——比手写随机交换省事得多。
- 注意：它只接受 **List**，Set / Map 传不进去（它们本来就没有"顺序位"可以打乱）。

```java
Collections.shuffle(students);   // 打乱后按顺序取前 N 个，就是随机抽取
```

**③ 踩到的坑：`while (sc.hasNext())` 会卡住**

现象：程序运行后没输出、也没反应，像卡死了。

原因：`Scanner.hasNext()` **本身就是阻塞的**——它会停下来等键盘输入，读到东西才返回 `true`。

所以顺序很关键：

```java
// ❌ 错：先判断 hasNext，程序停在这一行等输入，用户看不到任何提示
while (sc.hasNext()) {
    System.out.print("请输入：");   // 这句永远等不到执行
    ...
}

// ✅ 对：提示放前面，用户知道该输入了
System.out.print("请输入：");
while (sc.hasNext()) {
    ...
}
```

**一句话记住：`hasNext()` 会等输入，所以任何"告诉用户该输入了"的提示，必须写在它前面。**

## 🔍 自测（先遮住答案）

> [!question]- Q1：容量 16、负载因子 0.75，放第几个元素时会触发扩容？
> 放第 **13** 个时触发。
> 因为阈值 = 16 × 0.75 = **12**，size 超过 12（也就是到 13）就扩容。
> 所以"装到 75%"说的是 12 个，不是 16 个。这个数字很多人会记成 16。

> [!question]- Q2：为什么 Java 要把 HashMap 容量强制成 2 的幂？
> 因为计算数组下标用的是 `(n - 1) & hash`。
> 当 n 是 2 的幂，`n - 1` 的二进制全是 1，位与的结果正好落在 `0 ~ n-1` 之间，等价于取模，但**快得多**。
> 如果 n 不是 2 的幂，这个位运算结果会超出范围，就不能用了。

> [!question]- Q3：`while (sc.hasNext())` 为什么会让程序看起来卡死？
> 因为 `hasNext()` 是阻塞调用——它在等标准输入，没有输入就停在那一行不返回。
> 如果提示语写在循环体内，程序根本没走到打印那一步，用户看到的就是黑屏。
> 所以提示必须写在 `while` **之前**。

## 📎 补充：几个今天值得记住的

> [!note] 1. 转红黑树的阈值有两个，别只记 8
> 很多人只记得"链表 8 个转红黑树"，漏掉**数组 ≥ 64** 这个条件。
> 数组还小的时候优先扩容（打散更省事），扩容到 64 还不够才转树。
> 反过来，删到 **≤ 6** 个会退回链表（留了 2 的缓冲，避免在 7~8 之间反复横跳）。

> [!note] 2. `Collections.shuffle` 不给你新列表
> 它是原地打乱，返回 `void`。这点和很多"返回新对象"的工具方法不一样。
> 如果你想保留原顺序，得先 `new ArrayList<>(原list)` 复制一份再打乱。

> [!note] 3. Scanner 的坑不止一个
> 除了 `hasNext()` 阻塞，还有一个经典问题：`nextInt()` 之后紧接着 `nextLine()`，`nextLine()` 会读到空字符串。
> 原因是 `nextInt()` 没吃掉回车符，`nextLine()` 把它读走了。以后写交互程序一定会撞上。
