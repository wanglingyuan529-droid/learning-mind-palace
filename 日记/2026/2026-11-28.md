### Java · Commons-io 与 Maven

**Commons-io**：Apache 出的 IO 工具包，把 `FileUtils.readFileToString(f)` 这种操作从一堆流的嵌套压成一行。

**两种引入方式**（你都写了，而且自己用的是第二种）：

| 方式 | 做法 | 评价 |
| --- | --- | --- |
| 老式：手动 jar | 建 `lib/` → 拖 jar → Add as library | IDEA 里的操作，**现在少用** |
| 现代：构建工具 | 在 `pom.xml` 写 `<dependency>` | 自动从仓库拉，还能管版本传递 |

**关于你说的"Maven 对标 Python 的 uv"**——方向对，补一点：Maven 不只是**包管理器**（拉依赖），它还管**构建**（编译、打包、跑测试）。Python 那边对应的是 `uv` + `setuptools` 两件事合起来。

### Java · Properties 配置文件

**是什么**：专门读写 `key=value` 格式的配置文件，每行一对。

```properties
jdbc.url=jdbc:mysql://localhost:3306/db
jdbc.user=root
```

**你说的"支持中文但要注意编码"——这里有个具体原因**：

`Properties` 的默认编码是 **ISO-8859-1**（不是 UTF-8）。直接写中文会变乱码。两种解法：

```java
// ① 明确指定 Reader 的编码（推荐）
props.load(new InputStreamReader(new FileInputStream(f), StandardCharsets.UTF_8));

// ② 用 JDK 9+ 的 store/load 带 charset 参数的重载
```

### Docker · 镜像到底是个什么东西

**定义**（你抄的教程原文，是准确的）：镜像是一个**轻量、可独立执行的软件包**，包含运行某个软件所需的所有内容——应用、依赖、配置、运行环境。

**⚠️ 但你那个类比要改**：

> 类似 java 中 new 出来的一个对象

**不对。镜像是「类」，容器才是 `new` 出来的「对象」。**

| Java | Docker |
| --- | --- |
| **类**（模板，只定义不用） | **镜像**（只读模板） |
| `new` 出来的**对象**（真正干活） | **容器**（真正跑起来的实例） |

所以：**一个类能 new 出多个对象，一个镜像能启动多个容器**——这正是这个类比的正确用法，只是指错了位置。

### Docker · 分层与 UnionFS

**UnionFS（联合文件系统）**：一种**分层**的文件系统，把多个目录"叠"成一个看起来完整的文件系统。

**你写的理解是对的**：

> 一次同时加载多个文件系统，但从外面看只能看到一个

这就是"联合"的意思——**叠起来用，对外只露一个**。

**两个关键性质**：

| 层 | 可读写 | 说明 |
| --- | --- | --- |
| **镜像层**（下层） | **只读** | 一旦构建就不再变，多个容器共享 |
| **容器层**（最上层） | **可写** | 每个容器独立有一层，改动都落在这里 |

**所以容器删了，改的东西也没了**（它们只在最上面那层可写层里），**但镜像完好无损**——这正是镜像能被反复复用的原因。

### Docker · bootfs 与 rootfs

你的笔记基本照抄了教程，内容是对的，但有一处**实际使用中要修正**：

| 层 | 是什么 | 在 Docker 里的实际状态 |
| --- | --- | --- |
| **bootfs** | bootloader + kernel，系统启动时用 | **容器不加载自己的 kernel**，共享宿主的。所以容器镜像里 bootfs 基本是空的 |
| **rootfs** | 文件系统本体（各种目录、命令、库） | **这才是镜像里实实在在的东西** |

教程里那段"bootfs 加载完内核进内存、然后卸载 bootfs"是**Linux 系统启动的过程**，不是容器启动的过程。容器**没有自己的内核**（11-11 已经订正过一次这个点），所以容器启动时根本不走 bootfs 那套。

**一句话**：`rootfs` 是镜像的内容，`bootfs` 是宿主机的事。

### MySQL · 建库与四类 SQL

**基础命令**：

```sql
SHOW DATABASES;                    -- 看所有库
SELECT DATABASE();                 -- 看当前在哪个库
CREATE DATABASE [IF NOT EXISTS] 名字 DEFAULT CHARSET utf8mb4 COLLATE utf8mb4_general_ci;
DROP DATABASE 名字;
USE 名字;
```

**SQL 四类**（你写的分类是对的）：

| 类别 | 全称 | 管什么 | 代表 |
| --- | --- | --- | --- |
| **DDL** | Data **Definition** | **结构** | `CREATE` / `DROP` / `ALTER` |
| **DML** | Data **Manipulation** | **数据增删改** | `INSERT` / `UPDATE` / `DELETE` |
| **DQL** | Data **Query** | **查数据** | `SELECT` |
| **DCL** | Data **Control** | **权限** | `GRANT` / `REVOKE` |

**字符集 vs 排序规则**（你写得很准）：

| | 管什么 | 例子 |
| --- | --- | --- |
| **charset** | 存哪些字符、每个占几字节 | `utf8mb4` |
| **collate** | 字符怎么比较、怎么排序 | `utf8mb4_general_ci`（`ci` = 不区分大小写） |

**今天两个非常值钱的结论**（都是你自己写出来的）：

> 浮点二进制无法精确表示 0.1，金额、计数一律用 DECIMAL

✅ **完全正确**，而且是新手最容易踩的坑。`0.1 + 0.2` 在 `double` 里等于 `0.30000000000000004`。金额用 `DECIMAL(10,2)`。

> DDL 是隐式提交，回滚不了

✅ **也完全正确**。`CREATE` / `DROP` / `ALTER` 一旦执行**立刻生效**，没有 `ROLLBACK` 的机会。这意味着：写 DDL 之前**必须确认数据库名**。

## 💭 今天那段困惑：关于「要不要手搓」和「八股文」

你写了两段话，我把它拆成三个问题分别看：

### 问题一：「用 AI 生成代码，我能看懂就行，不确定这样对不对」

**答案是：对一半。** 关键在于"看懂"这三个字有深浅：

| 层次 | 能做什么 | AI 能不能替代你 |
| --- | --- | --- |
| **看懂它在干嘛** | 知道这是"读文件" | 能——这是最浅的一层 |
| **判断它对不对** | 发现它少了个 `close()` | **不能**，这需要真的懂 |
| **能改、能调** | 出错时定位到是哪一行的问题 | **不能**，这是最难的一层 |

**核心差别**：AI 生成的是**平均正确**的代码，但它不知道你的具体场景。改需求的时候，你得知道该动哪里——那就需要第二种能力。

所以"能看懂"如果是"能判断对错、能改"，那就够；如果是"大概知道它干嘛"，那不够。

### 问题二：「为什么公司招人还在考八股文，我不会也能正常开发」

这话有一半是对的，但原因不是"公司落后"：

**① 八股文是低成本的筛选信号**。面试 300 个人，让每个人都写真实项目代码不现实。考概念能在 30 分钟内把"完全没接触过"的人筛掉——**它考的不是记忆力，是有没有真的摸过这些技术**。

**② 很多八股文对应的场景确实天天在发生**。比如：
- 为什么 `ArrayList` 中间插入慢 → 真的会写出性能问题
- 为什么金额不用 `double` → 真的会算出账目对不上（**你今天刚学到这条**）
- 什么情况下线程不安全 → 真的会偶发 bug

这些不是背定义，是**避免踩坑**。

**③ 还有个现实**：招聘的人自己也只会这些。这不是理想状态，但它是当前的游戏规则。

### 问题三：「手搓太耗费时间了」

**这个抱怨是合理的，而且我同意一半。**

合理的部分：**不需要手写的东西，就别手写**。查文档、用工具类、让 AI 生成样板代码，这些都是提效，不是偷懒。

不同意的部分：**有些东西"手搓"一次的价值，不在记住，在建立直觉**。比如：

| 手搓一次 | 之后能干什么 |
| --- | --- |
| 你今天写的 `FileInputStream` 嵌套 | 报 `Stream Closed` 时知道是**哪一层**没关 |
| 一次缓冲流 vs 普通流的对比 | 知道什么时候该用哪个，而不只是"听说缓冲流快" |
| 你自己写 Properties 的编码问题 | 遇到乱码时知道该查编码，而不是瞎试 |

**这不是要求你背下来，是要求你"碰过一次"**。碰过一次之后，AI 给你代码时你才有能力判断它对不对。

> **一句话总结**：AI 能替你做"你会的部分"，替不了你做"你不会的部分的调试"。手搓的成本在前，收益在后——出问题那天。

## 🔍 自测（先遮住答案）

> [!question]- Q1：为什么容器删了，里面改的文件就没了，但镜像还在？
> 因为**镜像是只读的，容器在你改东西时，改动只写进最上面那层「可写层」**。
> 删容器 = 删掉那层可写层，下面的镜像层原封不动。
> 这也解释了为什么"一个镜像能启动多个容器"——每个容器各自有一层可写层，互不干扰。

> [!question]- Q2：DDL 不能回滚，那实际操作时怎么保护自己？
> 三个习惯：
> 1. **执行前先 `USE` 确认当前库**，`SELECT DATABASE()` 看一眼
> 2. `DROP` / `TRUNCATE` 之前先 `SELECT` 一下确认是对的表
> 3. 生产环境通常**先备份**，或者用 `CREATE TABLE ... AS SELECT` 留个快照
>
> 这就是"隐式提交"的实际后果——**它没有后悔药**。

> [!question]- Q3：`Properties.load()` 默认什么编码？为什么中文会乱码？
> 默认是 **ISO-8859-1**（这是 `Properties` 的历史包袱，从 JDK 1.0 就定了）。
> 中文在 ISO-8859-1 里存不了，所以要么被转义成 `\uXXXX`，要么直接乱码。
> 解法是传一个 `Reader` 进去并指定 UTF-8，别用默认的 `InputStream` 重载。

## 📎 补充：三个值得记住的

> [!note] 1. `DECIMAL` 的写法
> ```sql
> DECIMAL(10, 2)   -- 总共 10 位，其中 2 位是小数
> ```
> 意思是**整数部分最多 8 位、小数 2 位**，总长 10。金额、计数、任何需要精确的地方都用它，**永远不用 `FLOAT` / `DOUBLE`**。

> [!note] 2. `utf8mb4` 才是"真的 utf8"
> MySQL 里的 `utf8` 是个**历史遗留**——它其实只支持最多 3 字节的字符，存不了 emoji（emoji 是 4 字节）。
> 想要完整的 Unicode，必须写 **`utf8mb4`**。这是个经典坑，很多老项目还在用错的写法。

> [!note] 3. Maven 的依赖传递
> `Commons-io` 自己依赖别的库时，Maven 会**自动把它们也拉下来**，不用你手动一个个加。
> 这是它比"手动拖 jar"最大的优势之一——**手动时代，少拖一个 jar 就会报 `ClassNotFoundException`**。
