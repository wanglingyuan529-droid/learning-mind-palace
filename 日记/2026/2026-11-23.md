# 2026-11-23 学习日记

> 停了几天，今天重新开工。两块：终端 / shell / 内核的分工，和 IO 流的开头。

## 🎯 今天一句话

**终端负责"显现"，shell 负责"解释"，内核负责"执行"——三者分开，换个终端照样能干活，这才是它们能各自演化的原因。**

## ✅ 学到了什么

### 基础 · 终端 / shell / 内核

你那个比喻很准：**终端是餐桌，shell 才是做饭的**。补完整就是一条链：

```
键盘输入 → 终端（显示与交互） → shell（解释命令）→ 系统调用 → 内核（真正执行）
                                    ↑
                          bash / zsh / fish / sh
```

| 角色 | 干什么 | 换掉它会怎样 |
| --- | --- | --- |
| **终端** | 负责显示和输入 | 只影响速度、外观、快捷键，**执行结果不受影响** |
| **shell** | 解析你打的命令，决定调谁 | 换 shell 影响**语法和体验**（`fish` 更智能，`bash` 更通用） |
| **内核** | 真正干活（读写文件、调度进程） | 换内核是换操作系统 |

**所以"终端只是展示"这句话是对的**，而且它有个直接推论：**同一台机器可以同时开好几个终端，各自跑不同的 shell，互不干扰**。这在内核看来就是几个普通进程。

一个术语补充：现在说的"终端"基本都是**终端模拟器**（terminal emulator）——真终端（电传打字机那种硬件）早就不用了，现在的只是"假装自己是台老终端"的软件，所以叫模拟器。

### Java · IO 流是什么

**IO = Input / Output**，站在**程序**的角度看：

- **Input**：数据**流进**程序 ↔ 从文件读
- **Output**：数据**流出**程序 ↔ 写进文件

这个视角很重要。同样的"文件拷贝"，在程序眼里是 `Input`（读源文件）+ `Output`（写目标文件），两边都从程序出发。

**和昨天学的 File 接上了**：

> File 只能操作文件和目录**本身**，不能读写其中的**内容**。

这正是 IO 流存在的理由：**File 管"这个文件存不存在、叫什么、多大"，IO 流管"里面的字节怎么搬"**。

### Java · 字节流 vs 字符流

| | 字节流 | 字符流 |
| --- | --- | --- |
| 单位 | `byte`（8 位） | `char`（16 位） |
| 基类 | `InputStream` / `OutputStream` | `Reader` / `Writer` |
| 处理什么 | **一切**（任何二进制文件） | 主要文本 |
| 编码 | **不涉及** | **必须指定字符集** |
| 举例 | 图片、视频、zip、exe | txt、csv、java 源码 |

**你总结的那句是全对的**："字节流通用，字符流一般传文本；字节流不涉及编码，字符流涉及字符集。"

**最重要的一层**：**字符流的底层就是字节流 + 编码转换**。

```
FileReader = FileInputStream + 编码解码器
```

所以字符流不是独立的另一套，是**在字节流上包了一层"按编码翻译"**。理解了这条，`InputStreamReader`（把字节流转成字符流）那个类也就顺理成章了。

### Java · 今天学到的几个关键点

| 点 | 说明 |
| --- | --- |
| `FileInputStream` / `FileOutputStream` | 最基础的字节流实现类 |
| **一次读一个字节太慢** | 每次 `read()` 都是一次系统调用，开销是固定的 |
| **用数组批量读** | 常见缓冲大小 **8KB（8192 字节）**，不是随便写的 |
| **try-with-resources** | JDK 7+，只要资源实现了 `AutoCloseable`，退出 try 块自动 `close()` |

**批量读的写法**（今天练的核心）：

```java
byte[] buf = new byte[8192];        // 8KB 缓冲
int len;
while ((len = fis.read(buf)) != -1) {   // len 是这次实际读到的字节数
    fos.write(buf, 0, len);         // 注意写 len，不是写 buf.length
}
```

⚠️ 最后一行的 `0, len` 是坑点，见下文。

## 🔍 自测（先遮住答案）

> [!question]- Q1：为什么批量读要用"读到的长度 `len`"，而不是固定写 `buf.length`？
> 因为最后一次读**不一定读满**。
> 假设文件 10000 字节，缓冲 8192：第一次读满 8192，第二次只读到 1808 字节就碰到文件末尾了。
> 如果这时写 `buf.length`（8192），就会把缓冲区里**上一次残留的 6384 个字节**也写进去，目标文件末尾多出一堆垃圾。
> 所以必须写 `fos.write(buf, 0, len)`——**只写这次真正读进来的部分**。

> [!question]- Q2：`FileInputStream.read()` 为什么返回 `int` 而不是 `byte`？
> 因为要留一个"**表示读完了**"的特殊值——`-1`。
> `byte` 的范围是 -128~127，**-1 本身是个合法的字节值**（0xFF），没法区分"读到了 0xFF"和"读完了"。
> 所以 Java 把它提升成 `int`：`0~255` 表示真实字节，`-1` 单独表示结束。

> [!question]- Q3：字符流的底层为什么是字节流？
> 因为**文件里存的本来就是字节**，没有"字符"这种东西。字符是解码之后才存在的概念。
> 硬盘上是一串二进制，怎么切成"字符"取决于编码（UTF-8、GBK……）。
> 所以字符流 = 字节流 + 一层"按指定编码翻译"。`FileReader` 内部就是包了一个 `FileInputStream`。

## 📎 补充：对照教程补全的几点

> [!note] 1. IO 流的四大基类
> 你只学了 `FileInputStream` / `FileOutputStream`，但整个 IO 体系是**四个基类**搭起来的：
>
> | | 字节 | 字符 |
> | --- | --- | --- |
> | 输入 | `InputStream` | `Reader` |
> | 输出 | `OutputStream` | `Writer` |
>
> 所有具体的流（File、Buffered、Object、Data…）都是这四个的**子孙**。记住这四个，后面学什么都不迷路。

> [!note] 2. 为什么 8KB 这个数字好用
> 系统调用的开销是**固定**的（不管读 1 字节还是 8KB），所以一次读得越多，摊到每字节的成本越低。
> 但也不能无限大：数组要占内存，太大反而浪费、也不再提升。
> 8KB 是长期实践下来的折中值，很多库（包括 JDK 内部）都用 8192。

> [!note] 3. try-with-resources 的两个细节
> ```java
> try (FileInputStream in = new FileInputStream("a.txt");
>      FileOutputStream out = new FileOutputStream("b.txt")) {
>     // ...
> }   // 这里自动关闭，顺序是【逆序】：先关 out，再关 in
> ```
> - 多个资源用**分号**分隔
> - 关闭顺序是**反的**（先创建的后关），因为后建的往往依赖先建的
> - 关闭异常不会吞掉业务异常的，它会作为 **suppressed** 挂上去
