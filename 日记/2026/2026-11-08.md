# 2026-11-08 学习日记

> 今天两块硬骨头：斗地主项目的两种排序思路，和不可变集合的一整套规则。

## 🎯 今天一句话

**斗地主的两种排序，本质是同一招：把「比大小」这件事，翻译成「比整数」——一个靠手动编号，一个靠公式算权重。**

## ✅ 学到了什么

### Java · 斗地主：准备牌 / 洗牌 / 发牌

**项目主干**（教程里叫"准洗发"，其实是**准备牌、洗牌、发牌**三步的连读）：

```java
// ① 准备牌：静态代码块，类加载时执行一次
static {
    // 54 张牌塞进 ArrayList
}

// ② 洗牌：一行
Collections.shuffle(poker);

// ③ 发牌：循环 + 取模，轮流发给 3 个人
// ④ 看牌：打印
```

**为什么准备牌用静态代码块**：静态代码块在**类加载时执行一次**，不用 `new` 对象就能把牌准备好。适合"程序一跑就要存在一份"的静态资源。

### Java · 两种排序思路（今天重点）

**方法一：序号映射法**——给每张牌手动指定一个唯一的序号

```
3♣ → 0    3♦ → 1    3♥ → 2    3♠ → 3
4♣ → 4    4♦ → 5    ...
```

排序时按序号排，序号顺序就是你想要的牌序。**核心思想**：如果原始数据的规律太复杂，就手动建立"数据 → 唯一序号"的映射，把复杂比较变成整数比较。

**方法二：权重公式法**——现算一个数字权重，再比大小

$$\text{权重} = \text{点数} \times 10 + \text{花色}$$

比如 `♥K` = 13×10 + 2 = 132，`♠A` = 14×10 + 3 = 143，一比大小就出来了。

**两种方法本质是同一件事**：绕开"牌怎么比大小"这个复杂问题，**把它翻译成整数比较**。区别只在于序号是手写的，权重是算出来的。

⚠️ 但权重公式有个隐藏前提，见末尾订正第 1 条。

### Java · 不可变集合（Immutable）

**定义**：创建之后就不能改的集合，只能读，不能写。

**存在的三个意义**（你归纳的，全部准确）：

| 意义 | 说明 |
| --- | --- |
| **防意外修改** | 和封装是同一个思路：不给改的口子，就改不坏 |
| **线程安全** | 没有写操作，就不存在多线程打架 |
| **可当常量** | 定下来就不再变，适合做配置、字典、白名单 |

**五条硬规则**：

| 规则 | 表现 |
| --- | --- |
| 任何写操作都抛异常 | `add` / `remove` / `put` → `UnsupportedOperationException` |
| **不能放 null** | 内部用 null 表示数组空位，所以 `List.of(null)` 直接 `NullPointerException` |
| **Set / Map 不能有重复** | 而且**创建时就抛异常**，不是像普通 Set 那样静默去重（见补充 1） |
| `Map.of` 最多 10 对 | 超过 10 对必须用 `Map.ofEntries(...)` |
| **视图 ≠ 拷贝** | `unmodifiableList` 是**包装视图**，`copyOf` 是**真拷贝** |

**视图和拷贝的区别**（最容易懵的一节）：

```java
List<String> src = new ArrayList<>(List.of("a", "b"));
List<String> view = Collections.unmodifiableList(src);  // 视图
List<String> copy = List.copyOf(src);                   // 拷贝

src.add("c");
// view 现在也是 ["a","b","c"] —— 它是镜子
// copy 还是 ["a","b"]        —— 它是照片
```

**最关键的一句**：不可变集合只保证**集合结构**不变，**元素本身如果是可变对象，照样能改**。

```java
List<StringBuilder> list = List.of(new StringBuilder("abc"));
list.get(0).append("def");   // 合法！结构没变，改的是元素内部
```

## 🔍 自测（先遮住答案）

> [!question]- Q1：为什么要给每张牌映射一个序号，而不直接比大小？
> 因为"牌"是对象，比大小需要写一堆 if-else 判断点数再判断花色，又长又容易错。
> 而**整数比较是现成的、不会错的**。
> 映射序号（或算权重）本质是**把"业务规则的比较"降维成"数字比较"**——这是很通用的技巧，不止用在扑克上。

> [!question]- Q2：`Collections.unmodifiableList(list)` 之后，原 list 还能改吗？改了会怎样？
> 原 list **照样能改**——`unmodifiableList` 只是给你套了个"只读外壳"，它没动原集合。
> 而且你改了原 list 之后，那个只读视图里的内容**也跟着变**，因为它俩指向同一份数据。
> 想要真正独立的快照，得用 `List.copyOf()`。这个区别在实际项目里经常出事故。

> [!question]- Q3：不可变集合为什么不允许放 null？
> 因为 JDK 的实现里**用 null 表示数组的空槽位**（占位标记）。
> 如果允许你存 null，就没法区分"这里没元素"和"这里的元素是 null"。
> 所以干脆禁止，`List.of(null)` 直接抛 NPE。

## 📎 补充：三个今天值得记住的

> [!note] 1. `Set.of("a", "a")` 是**报错**，不是去重
> 普通的 `HashSet` 加重复元素是静默忽略（返回 false）。
> 但 `Set.of(...)` 遇到重复参数会直接抛 `IllegalArgumentException`。
> 同理 `Map.of(k, v, k, v2)` 键重复也抛异常。
> **不可变集合在创建时就校验，不给"悄悄去重"的机会。**

> [!note] 2. verification 和 validation 不是一回事
> 这两个词在软件工程里是专有名词，方向相反：
> - **verification**（验证）：我们**做的东西对不对**（符合规格吗）→ "Are we building the product right?"
> - **validation**（确认）：我们**做的是不是对的东西**（满足需求吗）→ "Are we building the right product?"
>
> 一句话：verification 对着**规格**，validation 对着**用户**。

> [!note] 3. `Arrays.asList()` 既不是不可变，也不是标准 List
> 它返回的是固定长度的列表：`add`/`remove` 会抛异常（像不可变），但 `set` 可以改（不是不可变）。
> 而且它跟原数组**共享同一份数据**——改数组，列表跟着变。
> 想清楚要哪种，别把这三样混了：`List.of`（真不可变）、`Arrays.asList`（固定长度可改值）、`Collections.unmodifiableList`（视图）。

## ⚠️ 一处要订正

> [!warning] 权重公式「点数 × 10 + 花色」——能跑，但前提是花色数少于 10
> 这个公式的思路是对的：**乘 10 把点数"抬高一个数量级"，加花色放在低位**，这样点数优先、花色次之。
>
> 但它是**靠"花色最多 4 种"这个事实兜住的**——只要花色数 < 10，低位就不会进位到高位。
> 如果哪天牌的花色变成 15 种，`点数×10 + 花色` 就会串位：`3 × 10 + 12 = 42`，比 `4 × 10 + 0 = 40` 还大，顺序全乱。
>
> **更稳的写法是乘"花色总数"而不是固定 10**：
> ```java
> int weight = point * 4 + suit;   // 4 = 花色总数，天然不进位
> ```
> 这样花色数量变了公式依然成立。**写死魔数 10 能跑，但埋了个雷。**
